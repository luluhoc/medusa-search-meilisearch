# Multiple languages

A search index holds the text it was seeded with. Searching a French catalogue therefore means indexing it in French — no query-time option can make an English index match `chemise`. This package handles that by declaring **one index per language** and routing each request to the index that holds the language it asked for.

Declare the languages once:

```ts
// src/search/product.ts
import { defineProductSearchIndex } from '@luluhoc/medusa-search-meilisearch/indexes'

export default defineProductSearchIndex({
  default_locale: 'en-US',
  locales: ['fr-FR', 'de-DE'],
})
```

That declares three indexes — `product`, `product-fr-FR`, `product-de-DE` — each seeded in its own language, each tokenized by its own analyzer, and each reindexed when a product, a variant or a translation for it changes.

Then search in a language rather than in an index:

```bash
curl '/store/meilisearch/products?query=chemise&locale=fr-FR'
```

`locale` is Medusa's own store parameter (or the `x-medusa-locale` header). It already decides which language the products come back in; here it also decides which index is searched, so a storefront sets its language in one place.

## Prerequisites

Translations live in Medusa's Translation Module, behind the `translation` feature flag:

```ts
// medusa-config.ts
featureFlags: { translation: true },
modules: [{ resolve: '@medusajs/medusa/translation' }],
```

Without the flag, `locale` is ignored by `query.graph` and every index ends up holding the default language — the setup still works, it is just the same catalogue three times. Untranslated fields fall back to the default language per field, so a partially translated catalogue indexes cleanly rather than indexing blanks.

Declaring more languages means more documents: three languages is three times the catalogue. Meilisearch is comfortable with that at ordinary catalogue sizes; it is worth knowing before declaring twenty.

## What each option does

| Option           | Effect                                                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `locales`        | Declares one index per BCP 47 tag, named `<index>-<locale>`, on top of the default index the call already declares.              |
| `default_locale` | The language the default index already holds. Requests for it are served from that index instead of a copy that would repeat it. |
| `locale`         | The single language one index is read in. What `locales` sets on each index it declares; still available on its own.             |

`default_locale` is worth setting. Without it, `?locale=en-US` finds no index for English and falls back to the default one — the same documents, by a longer route — and `en-US` will not appear in the admin listing as the language that index holds.

Everything else about a localized index is the definition you wrote: the same fields, filters, events, `transform` and `batch_size`. Only the language inside the documents differs.

## Tokenization

Each localized index declares its own analyzer: `product-fr-FR` is tokenized as French, which is what makes elision (`l'écran` → `écran`) and French stemming work. The language is derived from the locale, dropping the region — `fr-CA` and `fr-FR` are both analyzed as French.

Declare `settings.locales` yourself to override that for every index in the fan-out — a catalogue mixing two scripts in the same field is the usual reason:

```ts
defineProductSearchIndex({
  locales: ['ja-JP'],
  settings: { locales: ['jpn', 'eng'] },
})
```

A language Meilisearch cannot analyze is indexed without a declared language rather than failing the migration; Meilisearch detects it per document, which is what it does for every index that declares nothing.

## Which index answers a request

For all four store routes, in order:

1. An explicit `index` parameter. Asking for an index by name gets that index, and it keeps the language it declared.
2. The index registered for the request's `locale`, e.g. `product-fr-FR` for `?locale=fr-FR`.
3. The index registered for the request's language without its region — `?locale=fr-CA` is served by `product-fr-FR` if that is what exists.
4. The default index.

Step 4 is deliberate: a storefront in a language nobody indexed gets untranslated hits rather than no hits.

The `language` parameter is unchanged and still means the analyzer to tokenize the query with. It is an override, not a content selector — set it only to search one index in a language other than its own.

## Keeping the languages current

A localized index subscribes to translation events as well as to its entity's own, so editing a French product title reindexes it in `product-fr-FR` and touches nothing else. Translations for variants reindex the product holding them, because a product's document carries its variants' titles.

Two limits worth knowing:

- **A deleted translation is not picked up.** The event carries the translation's id, and the row is already gone when it arrives, so there is nothing left to resolve the product from. The document goes back to the default language at the next reindex of that product.
- **Replacing `events` takes over routing entirely.** A custom list has to include the translation events itself:

  ```ts
  import { productSearchEvents, translationSearchEvents } from '@luluhoc/medusa-search-meilisearch/indexes'

  defineProductSearchIndex({
    locales: ['fr-FR'],
    events: [...productSearchEvents, ...translationSearchEvents, 'my.custom.event'],
  })
  ```

Rebuilding one language is an ordinary reindex of one index:

```ts
await search.reindex({ index: 'product-fr-FR' })
```

## Categories

The same options apply, and the same routing:

```ts
// src/search/category.ts
import { defineCategorySearchIndex } from '@luluhoc/medusa-search-meilisearch/indexes'

export default defineCategorySearchIndex({ default_locale: 'en-US', locales: ['fr-FR'] })
```

```bash
curl '/store/meilisearch/categories?query=chemises&locale=fr-FR'
```

## Searching from your own code

The routes are a convenience; `query.search` addresses an index by name:

```ts
await search.search({ entity: 'product-fr-FR', filters: { q: 'chemise' } })
```

## In the admin

The [Search index widget](admin.md#search-index) answers per language: one row per index holding products, each saying whether this product is in it and whether its copy is behind. A product that is indexed in English and missing in French is a row that says so, rather than something a merchant has to go looking for one index at a time. Selecting a row shows that language's document.

Reindexing from the widget routes the product's update event, which reconciles **every** index that declares it — all languages at once, not just the one on screen.

## Indexes named by hand

Naming indexes yourself still works and stays supported — one factory call per language:

```ts
// src/search/product-fr.ts
export default defineProductSearchIndex({ name: 'produits', locale: 'fr-FR', settings: { locales: ['fra'] } })
```

An index declared with a `locale` is registered under it whatever it is called, so `?locale=fr-FR` routes to `produits` without a storefront knowing its name, and it follows translation events like any other localized index.

## The alternative: one index, many analyzers

If your catalogue is not translated and you only want the right analyzers, keep one index and declare the languages on it:

```ts
defineProductSearchIndex({ settings: { locales: ['eng', 'fra'] } })
```

That changes tokenization, not content — one document per product, holding whatever language the catalogue is written in. It is the right choice for a single-language catalogue whose customers type in several, and the wrong one for a translated catalogue.
